# 02 — Data model (SQLite, v1.0.0)

Binding inputs: [`00-scope.md`](00-scope.md) (D1–D21), ADRs 0002/0004/0005/0006/0007/0008, [`CONTEXT.md`](../../CONTEXT.md). Legacy reference: [`docs/legacy/03-database-schema.md`](../legacy/03-database-schema.md). Fresh start (ADR 0004): no legacy import, no legacy shapes.

Labels: items not grounded in `docs/legacy/` or the ADRs are marked **ASSUMPTION**. Crate versions are **unverified** (not checked against Context7 or crates.io in this pass).

## 1. SQLite conventions

| Topic | Decision |
|---|---|
| File | `<data_dir>/yanto.db` (ASSUMPTION: `data_dir=/var/lib/yanto`, mode 0700; DB file 0600). One DB, one process. |
| Driver | `sqlx` with the `sqlite` feature (version unverified). |
| Per-connection pragmas | `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`, `temp_store=MEMORY`, `trusted_schema=OFF`. `foreign_keys` is per-connection in SQLite, so it is set in `SqliteConnectOptions`, never in a migration. |
| Pool shape | ASSUMPTION: 1 writer connection + N read connections. Write transactions use `BEGIN IMMEDIATE` to avoid `SQLITE_BUSY` upgrade failures. |
| Tables | All `STRICT` (SQLite >= 3.37, bundled by `libsqlite3-sys`; version unverified). Types limited to `INTEGER`, `REAL`, `TEXT`, `BLOB`. |
| IDs | `TEXT` primary key, `<prefix>_<24 hex>` (12 random bytes), same as legacy for log readability. Exceptions are noted. |
| Timestamps | **`INTEGER` unix milliseconds, UTC.** Chosen over ISO `TEXT` because comparisons, retention deletes, and index range scans need no parsing, and they map to `i64` without a time-parsing dependency. Rendered at the edge. Column suffix `_at`. |
| Booleans | `INTEGER NOT NULL CHECK (x IN (0,1))`. |
| Enums | `TEXT NOT NULL CHECK (x IN (...))`. |
| JSON columns | `TEXT` with `CHECK (json_valid(x))`; used only for opaque, never-queried-by-field payloads (`audit_logs.metadata`, `app_settings.value`). Anything that must be constrained or joined is relational (see `user_project_permissions`). |
| Secrets | Never plaintext. Encrypted columns end in `_enc` (section 3). Token lookups use `_hash` (SHA-256). |
| Case-insensitive names | `COLLATE NOCASE` on `users.username`; hostnames are stored lowercase with `CHECK (hostname = lower(hostname))`. |
| Foreign keys | Declared with explicit `ON DELETE`. Indexes are created on every FK child column. |
| Integrity | `PRAGMA integrity_check` and `foreign_key_check` run in `yanto doctor` and before every self-update. |
| Backup | Yanto's own DB is backed up with `VACUUM INTO '<path>'` (consistent under WAL, no downtime). |

## 2. Migration strategy

- Files: `crates/<db-crate>/migrations/NNNN_<slug>.sql` (ASSUMPTION: crate layout is decided in the architecture doc). Numbering is sequential, 4 digits.
- Embedded: `sqlx::migrate!("./migrations")` compiles the files into the binary. `sqlx-cli` is a dev tool only, pinned in `mise.toml`; the shipped binary needs no CLI.
- Applied at startup, before listeners bind, by the single Master process. SQLite's file lock replaces the legacy Postgres advisory lock.
- Forward-only: no `down` migrations. sqlx checksums applied files, so applied migrations are immutable; fixes are new migrations.
- Before applying any pending migration on an existing DB, write `<data_dir>/backups/pre-migrate-<version>-<ts>.db` via `VACUUM INTO` (ASSUMPTION; keeps last 3). Failure to migrate aborts startup and leaves the service down rather than serving a half-migrated schema.
- `0001_init.sql` is the whole v1.0.0 schema. There is no bridge or backfill code (contrast legacy `legacy-handwritten-schema` bridge).
- Table rebuilds (SQLite cannot drop constraints) use the create-new / copy / drop / rename recipe inside one transaction with `foreign_keys` temporarily off via `PRAGMA defer_foreign_keys`.
- `yanto migrate --check` reports pending migrations without applying (CLI, doc 03).

## 3. Secrets at rest

| Item | Rule |
|---|---|
| Algorithm | AES-256-GCM, 12-byte random nonce per value (ASSUMPTION: algorithm; legacy used AES-256-GCM). |
| Envelope | `enc:v1:<base64url nonce>:<base64url ciphertext||tag>`; the `v1` tag allows later rotation to a new algorithm. |
| AAD | `<table>.<column>.<row id>` is bound as additional authenticated data, so a ciphertext copied to another row or column fails to decrypt. |
| Master key | 32 random bytes, generated by `yanto install` with a CSPRNG. Stored at **`/etc/yanto/secret.key`**, owner root, mode 0600, directory 0700 (ASSUMPTION: path). Override with `--secret-key-file` / `YANTO_SECRET_KEY_FILE` (path only; the key itself is never accepted from an env var, risk area: secrets management). |
| Separation | The key lives outside `data_dir`, so Yanto SQLite Backups and `VACUUM INTO` copies do not contain it and cannot be decrypted alone. Operators must back up the key separately; `yanto doctor` warns if absent. Losing it makes every `_enc` column unrecoverable, and Yanto surfaces them as "needs re-entry" rather than failing startup. |
| Rotation | `yanto rotate-secret-key` (ASSUMPTION): decrypts and re-encrypts every `_enc` column in one transaction with a new key, then replaces the file atomically. Not required for v1.0.0 launch; the `v1` envelope tag and a `key_id` slot are reserved. |
| Memory | Decrypted values live in `secrecy`/zeroize-style wrappers and are never logged (crate choice unverified). |
| Token hashing | High-entropy random tokens (session, API Token, account token, Deploy Token bearer) are stored as SHA-256 hex. No KDF is needed because inputs carry 256 bits of entropy. Lookup is by hash, so no timing oracle on the secret. |
| Password hashing | `users.password_hash` and `registry_users.password_hash` hold salted slow hashes: Argon2id PHC string for users (ASSUMPTION), bcrypt `$2y$` for registry users (forced: `registry:2` htpasswd accepts only bcrypt). |

Secret inventory:

| Secret | Column | Storage |
|---|---|---|
| Owner/Member password | `users.password_hash` | Argon2id (ASSUMPTION) |
| Session id | `sessions.id` | SHA-256 of cookie value |
| API Token | `api_tokens.token_hash` | SHA-256; shown once at creation |
| Account token (invite/reset) | `account_tokens.token_hash` | SHA-256; shown once |
| Deploy Token | `projects.deploy_token_hash` + `projects.deploy_token_enc` | hash for bearer check; ciphertext for reveal and webhook HMAC key (see note) |
| Deploy Key private key | `deploy_keys.private_key_enc` | AES-GCM; written to a 0600 tmpfs file only for the duration of a clone |
| Registry Credential secret | `registry_credentials.secret_enc` | AES-GCM |
| Hosted Registry user | `registry_users.password_hash` | bcrypt; `htpasswd` file is derived |
| Cloudflare API token | `cloudflare_clients.api_token_enc` | AES-GCM |
| Tunnel connector token | `cloudflare_tunnels.tunnel_token_enc` | AES-GCM |
| frps dashboard password / auth token | `frps_settings.*_enc` | AES-GCM |
| Pending env on a queued deploy | `deployments.pending_env_enc` | AES-GCM; nulled when the run starts |
| One-time setup code | `app_settings` key `setup.code_hash` | SHA-256; row deleted on first Owner creation |

Note (Deploy Token): the scope asks for a hashed Deploy Token **and** reveal/rotate (parity checklist) **and** GitHub HMAC verification, which needs the secret in plaintext. These conflict if only a hash exists. Resolution (ASSUMPTION, flag in open questions): store both `deploy_token_hash` (fast bearer check, no decrypt on the hot path) and `deploy_token_enc` (reveal + HMAC key). Reveal is `secrets`-gated, audited, and `admin` + `confirm` over MCP.

### 4.1 Identity and access

#### `users`
Purpose: dashboard accounts. Exactly one Owner, DB-enforced.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, prefix `usr` |
| `username` | TEXT | NOT NULL, `COLLATE NOCASE`, `CHECK (length(username) BETWEEN 1 AND 200)`, UNIQUE |
| `role` | TEXT | NOT NULL, `CHECK (role IN ('owner','member'))` |
| `status` | TEXT | NOT NULL, `CHECK (status IN ('invited','active','disabled'))` |
| `password_hash` | TEXT | NULL while `invited` |
| `last_login_at` | INTEGER | NULL |
| `created_at`, `updated_at` | INTEGER | NOT NULL |

- `CREATE UNIQUE INDEX users_single_owner ON users(role) WHERE role='owner';`
- `CHECK (role <> 'owner' OR status <> 'disabled')`: Owner is never `disabled`. Also trigger `users_owner_immutable`: `BEFORE DELETE` aborts if `OLD.role='owner'`; `BEFORE UPDATE OF role` aborts when role changes to or from `owner`.
- `CHECK (status <> 'active' OR password_hash IS NOT NULL)`.
- Index: `users_status_idx(status)`.
- No `session_version` (legacy): revocation is deleting `sessions` rows.
- `owner-reset` CLI rewrites the Owner's password hash and deletes all that user's sessions.

#### `sessions`
Purpose: server-side dashboard sessions, revocable (parity: "sessions revocable server-side").

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK = SHA-256 hex of the cookie value (cookie value is 32 random bytes, base64url) |
| `user_id` | TEXT | NOT NULL, FK `users(id)` ON DELETE CASCADE |
| `csrf_token` | TEXT | NOT NULL (per-session synchronizer token; doc 03) |
| `created_at`, `expires_at`, `last_seen_at` | INTEGER | NOT NULL |
| `ip` | TEXT | NULL |
| `user_agent` | TEXT | NULL, truncated to 256 chars |

Indexes: `sessions_user_idx(user_id)`, `sessions_expires_idx(expires_at)`. Expired rows are purged by a periodic task. `last_seen_at` is updated at most once per minute to limit writes.

#### `account_tokens`
Purpose: single-use invite/reset tokens, 24h TTL.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `atk` |
| `user_id` | TEXT | NOT NULL, FK `users` CASCADE |
| `purpose` | TEXT | NOT NULL, `CHECK (purpose IN ('invite','reset'))` |
| `token_hash` | TEXT | NOT NULL, UNIQUE |
| `expires_at` | INTEGER | NOT NULL (`created_at + 86 400 000`) |
| `used_at` | INTEGER | NULL |
| `created_at` | INTEGER | NOT NULL |

Indexes: `account_tokens_user_active_idx(user_id, used_at)`, `account_tokens_expires_idx(expires_at)`. Issuing a reset: set `users.status='invited'`, null the password hash, delete sessions, insert the token, all in one transaction (legacy behavior). Completing setup marks every token for the user used.

#### `user_project_access`
Purpose: grants a Member visibility on a Project. Owner has no rows (bypasses). A row with zero permission rows means "can view the Project, nothing else".

| Column | Type | Constraints |
|---|---|---|
| `user_id` | TEXT | FK `users` CASCADE |
| `project_id` | TEXT | FK `projects` CASCADE |
| `created_at`, `updated_at` | INTEGER | NOT NULL |

PK `(user_id, project_id)`; index `user_project_access_project_idx(project_id)`. Trigger aborts inserts where the user is the Owner.

#### `user_project_permissions`
Purpose: per-Project permissions as rows, so the allowed set is a real `CHECK` (SQLite forbids sub-selects in CHECK, so a JSON array could not be validated in-DB).

| Column | Type | Constraints |
|---|---|---|
| `user_id`, `project_id` | TEXT | composite FK to `user_project_access(user_id, project_id)` ON DELETE CASCADE |
| `permission` | TEXT | `CHECK (permission IN ('deploy','runtime','config','secrets','backups','hostnames'))` |

PK `(user_id, project_id, permission)`. `tasks` is dropped (AI).

**App views are not stored.** They are derived from permissions at request time (legacy behavior): every Member gets `dashboard`, `projects`, `deployments`, `containers`, `audit`; any Project with `backups` adds the `backups` view; any with `hostnames` adds `hostnames`. Owner sees all views (the full list is in doc 03, section b). Rationale: avoids a second source of truth that can drift from permissions.

#### `api_tokens`
Purpose: scoped bearer tokens for REST and MCP. Replaces `mcp_access_tokens`.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `tok` |
| `name` | TEXT | NOT NULL, 1-100 chars, UNIQUE among non-revoked (partial unique index) |
| `token_hash` | TEXT | NOT NULL, UNIQUE (SHA-256 of the full token) |
| `token_hint` | TEXT | NOT NULL, first 8 chars of the random id part, for display only |
| `scope` | TEXT | NOT NULL, `CHECK (scope IN ('read','write','admin'))`; rank `read < write < admin` is applied in code |
| `created_by` | TEXT | FK `users` ON DELETE SET NULL |
| `expires_at` | INTEGER | NULL = no expiry (ASSUMPTION: optional expiry is new) |
| `last_used_at` | INTEGER | NULL; updated at most once per minute |
| `last_used_ip` | TEXT | NULL |
| `revoked_at` | INTEGER | NULL; soft revoke keeps audit linkage |
| `created_at` | INTEGER | NOT NULL |

Format (ASSUMPTION): `yat_<id-part>_<secret>`; the `ymcp_` format is not reused. Lookup computes SHA-256 of the presented token and selects by `token_hash` where `revoked_at IS NULL` and not expired. API Tokens are not Project-scoped (see doc 03 open question).

### 4.2 Projects and deployments

#### `projects`
Purpose: a deployable unit (Git or image source) run with Docker Compose.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `prj` |
| `name` | TEXT | NOT NULL, 1-100 chars |
| `slug` | TEXT | NOT NULL, UNIQUE, `CHECK (slug GLOB '[a-z0-9][a-z0-9_-]*' AND length(slug) <= 63)`. Is the Compose project name and on-disk directory name `<projects_root>/<slug>` (path is derived, not stored). Uniqueness makes container-to-Project mapping unambiguous, removing legacy's 409 "ambiguous folder" case. |
| `source_kind` | TEXT | NOT NULL, `CHECK (source_kind IN ('git','image'))` |
| `git_url` | TEXT | NULL |
| `branch` | TEXT | NULL |
| `image_ref` | TEXT | NULL; may point at the Hosted Registry (`127.0.0.1:5000/...`) |
| `compose_path` | TEXT | NOT NULL default `'docker-compose.yml'`; relative, `.yml/.yaml`, no `..` (validated in code and by `CHECK (compose_path NOT LIKE '/%' AND compose_path NOT LIKE '%..%')`) |
| `compose_content` | TEXT | NULL; pasted/inline compose written at deploy time; for image Projects, the generated compose |
| `env_file` | TEXT | NOT NULL default `'.env'`, same path rules |
| `auto_start` | INTEGER | boolean, default 1 |
| `manual_deploy_enabled` | INTEGER | boolean, default 1 |
| `github_webhook_enabled` | INTEGER | boolean, default 1 |
| `deploy_token_hash` | TEXT | NOT NULL (SHA-256) |
| `deploy_token_enc` | TEXT | NOT NULL (see section 3 note) |
| `deploy_key_id` | TEXT | FK `deploy_keys(id)` ON DELETE SET NULL |
| `registry_credential_id` | TEXT | FK `registry_credentials(id)` ON DELETE SET NULL |
| `created_at`, `updated_at` | INTEGER | NOT NULL |

Cross-column check: `CHECK ((source_kind='git' AND git_url IS NOT NULL AND branch IS NOT NULL AND image_ref IS NULL) OR (source_kind='image' AND image_ref IS NOT NULL AND git_url IS NULL))`.
Indexes: `projects_created_idx(created_at)`; FK indexes on `deploy_key_id`, `registry_credential_id`.
Dropped vs legacy: `local_path` (derived), `docker_image` empty-string sentinel (now NULL + `source_kind`), `target_node_id`, `agent_image`, `deploy_token` plaintext, `ssh_private_key_path`/`ssh_public_key` (moved to `deploy_keys`).
Deleting a Project cascades to ports, databases, deployments (and logs), hostnames, access rows; backups and audit rows keep history with `project_id` set NULL. The files on disk and the Compose stack are removed by the service layer before the row is deleted (not by the DB).

#### `project_ports`
Purpose: published loopback ports a Project declares (D: "Projects declare loopback-published ports; Yanto detects port collisions"). Hostnames target a row here.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `ppt` |
| `project_id` | TEXT | NOT NULL, FK `projects` CASCADE |
| `label` | TEXT | NOT NULL (e.g. `web`), UNIQUE per Project |
| `host_port` | INTEGER | NOT NULL, `CHECK (host_port BETWEEN 1 AND 65535)`, **UNIQUE across all Projects** |
| `container_port` | INTEGER | NOT NULL, 1-65535 |
| `bind_address` | TEXT | NOT NULL default `'127.0.0.1'`, `CHECK (bind_address IN ('127.0.0.1','::1'))` (loopback only, ADR 0006) |
| `protocol` | TEXT | NOT NULL default `'tcp'`, `CHECK (protocol IN ('tcp','udp'))` |
| `created_at` | INTEGER | NOT NULL |

Indexes: `UNIQUE(host_port)`, `UNIQUE(project_id, label)`. DB uniqueness covers Yanto-known ports; the service layer additionally checks Yanto's own port, the Hosted Registry port, `frps` ports, and ports already bound on the Host (live `bind` probe) before accepting a port. The declared ports are reconciled with the compose file at deploy time (a mismatch fails the Deployment with a clear log line).

#### `project_databases`
Purpose: lets a Project declare a Postgres/MySQL service so Backups can dump it (D14). ASSUMPTION: table is new; shape not in legacy (legacy auto-discovered Postgres containers).

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `pdb` |
| `project_id` | TEXT | NOT NULL, FK `projects` CASCADE |
| `engine` | TEXT | NOT NULL, `CHECK (engine IN ('postgres','mysql'))` |
| `compose_service` | TEXT | NOT NULL; UNIQUE with `project_id` |
| `database` | TEXT | NOT NULL |
| `user_env`, `password_env` | TEXT | NOT NULL; **names** of environment variables in the service, read via `docker exec`; credentials are never stored here |

#### `deployments`
Purpose: one attempt to bring a Project to a revision; also the queue.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `dep` |
| `project_id` | TEXT | NOT NULL, FK `projects` CASCADE |
| `status` | TEXT | NOT NULL, `CHECK (status IN ('queued','running','success','failed','cancelled','interrupted'))` |
| `trigger` | TEXT | NOT NULL, `CHECK (trigger IN ('manual','api','deploy_token','github','rollback','cron'))` (ASSUMPTION: `api`/`cron` are new; legacy had manual/webhook/github/rollback) |
| `triggered_by` | TEXT | NULL: actor label (`user:<id>`, `token:<id>`, `github`) |
| `target_ref` | TEXT | NULL |
| `commit_sha`, `commit_message` | TEXT | NULL, filled during run |
| `rollback_from_deployment_id` | TEXT | FK `deployments(id)` ON DELETE SET NULL |
| `pending_env_enc` | TEXT | NULL; env payload carried by the deploy, nulled at run start |
| `exit_code` | INTEGER | NULL |
| `error` | TEXT | NULL, short failure reason |
| `log_bytes` | INTEGER | NOT NULL default 0 |
| `log_truncated` | INTEGER | boolean default 0 |
| `queued_at` | INTEGER | NOT NULL |
| `started_at`, `finished_at` | INTEGER | NULL |

Queue and concurrency invariants (in the DB, not only in code):
- `CREATE UNIQUE INDEX deployments_one_running ON deployments(project_id) WHERE status='running';`
- `CREATE UNIQUE INDEX deployments_one_queued ON deployments(project_id) WHERE status='queued';` Enqueuing while one is queued returns the existing row (`reused`, like legacy) or replaces its target (ASSUMPTION: coalescing; legacy had no queue, only "reuse running").
- Scheduler picks `SELECT ... WHERE status='queued' ORDER BY queued_at LIMIT 1` per free slot; global concurrency is `app_settings` `deploy.max_concurrent` (ASSUMPTION default 2). The claim is `UPDATE ... SET status='running' WHERE id=? AND status='queued'` (row count 1 = won).
- Startup recovery: every `running` row becomes `interrupted` with `finished_at=now` and a system log line (replaces legacy "mark failed").
- Indexes: `deployments_project_queued_idx(project_id, queued_at DESC)`, `deployments_status_queued_idx(status, queued_at)`, `deployments_queued_at_idx(queued_at DESC)`.
- Retention (ASSUMPTION): keep newest 50 finished Deployments per Project (`deploy.retention_per_project`); pruning cascades to logs.
Dropped vs legacy: `node_id`, `logs` column (moved), `status='running'` as the only non-terminal state.

#### `deployment_logs`
Purpose: append-only log chunks. A separate table keeps appends cheap (legacy rewrote a growing `text` column with SQL-side truncation) and supports SSE resume by `seq`.

| Column | Type | Constraints |
|---|---|---|
| `deployment_id` | TEXT | FK `deployments` CASCADE |
| `seq` | INTEGER | NOT NULL, monotonic per Deployment |
| `ts` | INTEGER | NOT NULL |
| `stream` | TEXT | `CHECK (stream IN ('stdout','stderr','system'))` |
| `data` | TEXT | NOT NULL, <= 64 KiB per chunk |

`PRIMARY KEY (deployment_id, seq) WITHOUT ROWID`. The runner batches writes (ASSUMPTION: 250 ms / 64 KiB). Per-Deployment cap `runtime.deployment_log_max_bytes` (legacy had `deploymentLogMaxChars`): when exceeded, oldest chunks are deleted, a system "truncated" chunk is kept at the head, and `deployments.log_truncated=1` (tail kept, as legacy). SSE clients reconnect with `Last-Event-ID = seq`. Secrets: known secret values (env values of the Project, registry secret) are redacted by the runner before write (risk area: secrets management; ASSUMPTION).

#### `deploy_keys`
Purpose: SSH keys Yanto uses to clone private repos. Separate rows allow one key reused by several Projects (GitHub allows a deploy key on one repo only, so per-Project keys are the common case; sharing is for machine users).

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `dky` |
| `name` | TEXT | NOT NULL, UNIQUE |
| `key_type` | TEXT | NOT NULL, `CHECK (key_type IN ('ed25519','rsa','ecdsa'))` |
| `public_key` | TEXT | NOT NULL |
| `fingerprint` | TEXT | NOT NULL, UNIQUE (SHA256) |
| `private_key_enc` | TEXT | NOT NULL |
| `created_at` | INTEGER | NOT NULL |

Private key is in the DB (encrypted), not a file under `/tmp` (legacy default `/tmp/yanto-ssh`), so it is covered by DB backups and never sits unencrypted on disk. `projects.deploy_key_id` is `SET NULL` on delete, and deletion is blocked in the service layer while referenced (409 with the Project names).

#### `registry_credentials`
Purpose: login for external registries (GHCR, Docker Hub) used to pull private images.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `rcr` |
| `name` | TEXT | NOT NULL, UNIQUE |
| `registry_host` | TEXT | NOT NULL (e.g. `ghcr.io`) |
| `username` | TEXT | NOT NULL |
| `secret_enc` | TEXT | NOT NULL (password or PAT, AES-GCM envelope from section 3) |
| `created_at`, `updated_at` | INTEGER | NOT NULL |

Used with `docker --config <tmpdir> login --password-stdin` into an ephemeral per-deploy Docker config dir (ASSUMPTION), so the global `~/.docker/config.json` is never written. Secret is write-only in every adapter.

### 4.4 Host management

#### `cron_entries`
Purpose: rows rendered into `/etc/cron.d/yanto` (D11). DB is the source of truth; the file is regenerated whole and written atomically with mode 0644 and a "managed by Yanto, do not edit" header. Hand edits to the file are overwritten (shown as drift in the UI). Other cron files are read from disk, read-only, never stored.

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PK, `crn` |
| `name` | TEXT | NOT NULL, UNIQUE (rendered as a comment line) |
| `schedule` | TEXT | NOT NULL, 5-field cron or `@daily`-style alias, validated in code |
| `run_as_user` | TEXT | NOT NULL (each entry names its Unix user, per CONTEXT.md); must exist in `/etc/passwd` at write time |
| `command` | TEXT | NOT NULL, single line, no newline or `%` unescaped (cron treats `%` as newline; the renderer escapes it) |
| `enabled` | INTEGER | boolean default 1; disabled rows are omitted from the file |

## 6. Cross-cutting constraints summary

- Single Owner: partial unique index + triggers (users).
- One running and one queued Deployment per Project: partial unique indexes.
- Unique published port across Projects: `UNIQUE(host_port)`.
- Hostname uniqueness and provider/tunnel consistency: `CHECK`s on `hostnames`.
- Append-only audit: update trigger.
- Referenced credentials cannot be deleted silently: FK `SET NULL` plus service-layer 409 listing dependents; `cloudflare_tunnels` and `project_ports` use `RESTRICT`.

## 7. Open questions / risks

1. Deploy Token reversible storage (section 3 note) trades hash-only safety for reveal/HMAC. Alternative: separate webhook secret from bearer token, bearer hash-only, reveal = rotate-and-show.
2. Single-writer pool and long `VACUUM INTO` calls can stall writers; schedule off-peak.
3. `STRICT` + `json_valid` need SQLite >= 3.37; bundled version unverified.
4. Hostname/port cross-table consistency relies on triggers; test coverage required.
5. Registry users and htpasswd regeneration require bcrypt cost chosen vs registry request latency (unverified).
